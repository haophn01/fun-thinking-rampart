### DB: migration 0006 (D1)
- Generated by drizzle-kit from `schema.ts` as `0006_sec_auth`, then the trigger block below is appended before the first commit. Snapshots don't track triggers. No CHECK is added to an existing table, because drizzle-kit would rebuild it.
- **`user`** gains `must_change_password` (integer boolean, not null, default 0), `password_changed_at` (text), `mfa_secret_enc` (text), `mfa_last_step` (integer) and `mfa_enrolled_at` (text).
- **`session`** gains `locked_at` (text) and `mfa_pending` (integer boolean, not null, default 0; sec-mfa uses it).
- **`audit_event`** gains `prev_hash` and `hash` (text).
- **New tables:**
  - `password_history`: `id` integer pk autoincrement; `user_id` not null FK `user.id`; `password_hash` not null; `created_at` not null; index `(user_id, id)`.
  - `mfa_recovery_code`: `id` integer pk autoincrement; `user_id` not null FK; `code_hash` not null; `created_at` not null; `used_at`; index `user_id`.
  - `settings`: `id` integer pk with check `id = 1` (one row, created by the first write); `sign_in_notice` text; `updated_by` not null FK `user.id`; `updated_at` not null.
- **Trigger:** `DROP TRIGGER audit_event_no_update`, then `CREATE TRIGGER audit_event_no_update BEFORE UPDATE ON audit_event WHEN NOT (<fill-once>)`, which raises `audit_event is append-only`. `<fill-once>` holds only when all of these are true:
  - `OLD.hash IS NULL AND OLD.prev_hash IS NULL AND NEW.hash IS NOT NULL`
  - every other column is unchanged (`NEW.x IS OLD.x`)

  `audit_event_no_delete` is untouched.
- **Why the audit backfill waits for sec-integrity:** SQLite SQL has no SHA-256, and the canonical form is sec-integrity's to define. The narrowed trigger lets sec-integrity backfill in code, in one transaction after migrating, with no second migration. This sprint writes new events with null hashes, and the backfill fills them too.
- **Backup (orchestrator, before the wave-1 merge reaches the checkout the human's app runs from):** `pnpm dev` restarts the api through tsx watch and migrates as soon as `schema.ts` changes. In `apps/api`, run `node -e "const D=require('better-sqlite3');new D('data/rampart.sqlite',{readonly:true}).backup('data/rampart.pre-0006.sqlite').then(()=>console.log('backup ok'))"`. **Restore:** stop the app, copy `data/rampart.pre-0006.sqlite` over `data/rampart.sqlite`, delete `rampart.sqlite-wal` and `-shm`, then revert D1's merge commit.

### Sessions, lock and passwords (A1, `apps/api/src/auth/`)
- **Timeouts:** idle is `SESSION_IDLE_LIMIT_MS` after `last_seen_at`, and absolute is `SESSION_ABSOLUTE_LIMIT_MS` after `created_at`. A session ends at exactly the limit, so 29:59.999 idle passes and 30:00.000 fails. The cookie `Max-Age` is 28800. `IDLE_LIMIT_MS`, `ABSOLUTE_LIMIT_MS` and `SESSION_MAX_AGE_SECONDS` keep their names.
- **Rotation:** `rotateSession(tx, sessionId, now)` deletes the row and inserts one for the same user, with a new token, a new CSRF token and the **same `created_at`**, so the 8 h limit still counts from sign-in. It sets the cookie. Sign-in and setup keep making a fresh session, which also deletes the cookie's old one.
- **`ActiveSession`** gains `locked: boolean` and `mustChangePassword: boolean`; the guard reads `user` on every request. A **locked** session's `last_seen_at` is never moved, except by a successful unlock. So it ends 30 min after its last unlocked request.
- **Guard order:** 401 `unauthenticated` → 403 `csrf_failed` → 423 `session_locked` → 403 `password_change_required` → 403 `forbidden` → 400 → 404.
  - Public routes are never gated by lock or by a required password change.
  - Pinned lists in `guard.ts`: `LOCKED_SESSION_ROUTES = ['POST /api/session/lock', 'POST /api/session/unlock']`, and `PASSWORD_CHANGE_ROUTES` = those two plus `'POST /api/session/password'`. sec-mfa appends to them.
- **`GET /api/session`, setup and sign-in** report `locked`, `mustChangePassword`, and `signInNotice` (A1 sends `null`; N1 fills it). A locked session still gets its `user` and `csrfToken`.
- **Routes** (`auth/session-routes.ts`, inside the guarded plugin; session and CSRF needed):

  | Route | Success | Failures |
  |---|---|---|
  | `POST /api/session/lock` | 204. Sets `locked_at` if null and audits `auth.session_locked` once; repeats are 204 with no event | — |
  | `POST /api/session/unlock` `{ password }` | 200 `sessionResponse`. Clears `locked_at`, moves `last_seen_at`, audits `auth.session_unlocked` only if it was locked. No rotation (tabs share the cookie) | 401 `invalid_credentials`; 429 while the account is locked |
  | `POST /api/session/password` `{ currentPassword, newPassword }` | 200 `sessionResponse` with a rotated cookie. Every other session of the user ends. The old hash goes to history, and the new hash is stored. `must_change_password` is set false, `password_changed_at` to now, and the failure count to 0. Audits `auth.password_changed` with before and after null | 400, 401 `invalid_credentials`, `password_too_common`, `password_reused`, 429 |

  - Change order: body → account lock (429) → current password → blocklist → reuse.
  - `AUTH_LIMITED_ROUTES` appends `POST /api/session/password` and `POST /api/session/unlock`. Lock uses the general bucket.
- **Lockout (`auth/lockout.ts`)** moves out of `auth/routes.ts` with today's behaviour, and sign-in, unlock and change share it.
  - Failures from all three count in one run of 5. A locked account answers 429 and doesn't count the attempt.
  - When the 5th failure comes from a session (unlock or change), the same transaction also locks the account, ends **all** that user's sessions and clears the cookie, and the answer is 401 `unauthenticated`.
- **Password policy (`auth/password-policy.ts`):**
  - `checkNewPassword(pw)` throws `password_too_common` when P1's `isBlocklisted` says so.
  - Reuse means a match with the current hash or any of the user's newest `PASSWORD_HISTORY_DEPTH − 1` history rows. After P1…P6 are set in order, P2–P6 are refused and P1 is accepted.
  - History keeps the newest 4 rows per user; older rows are deleted.
  - Setup checks the blocklist and sets `password_changed_at`. Users' create and reset (U1) check the blocklist only.

### Temporary passwords and sign out everywhere (U1, `users/routes.ts`)
- `POST /api/users`, and a `PATCH` with `password`, set `must_change_password = true` and `password_changed_at = now` (the password is temporary). A reset also moves the old hash into history and ends all the user's sessions (as today). Yourself included.
- A `PATCH` that really changes `role` ends all the target's sessions. For yourself it also clears the cookie, as reset does. Display name and reactivation end nothing, and a same-value role is a no-op.
- A blocklisted temporary password → 400 `password_too_common`, with nothing changed.
- **Harness:** `signIn(email, password, { temporary?: boolean })` clears `must_change_password` in the DB before signing in, unless `temporary: true` is passed. Existing suites stay green unchanged.

### Sign-in notice (N1)
- **`PUT /api/settings/sign-in-notice`** (admin, CSRF) `{ text }` → 200 `signInNoticeResponse`.
  - It audits `settings.updated` (entity `settings`/`sign_in_notice`, before and after `{ signInNotice }`).
  - Saving the same text is 200 with no event.
  - `ROUTE_MATRIX` entry: access `admin`, `idor: { notApplicable: 'one global setting' }`.
- **`digest`** is the lowercase SHA-256 hex of the stored text (UTF-8). `GET /api/session` sends `signInNotice` to everyone, signed in or not.
- **Sign-in with a notice set:** order is body → notice → account lock → password.
  - A missing or stale `noticeDigest` → 400 `notice_not_acknowledged`, with no failure counted and no event.
  - A successful sign-in writes `auth.notice_acknowledged` (entity the user, `after: { digest }`) before `auth.signed_in`, in its transaction.
  - With no notice, a sent digest is ignored. Setup is never gated.

### Web (G1 builds the seams; W1–W3 fill the stubs)
- **`useSession()`:**
  - The statuses are `loading | setup | signed_out | signed_in | locked | password_change | error`. `locked` wins over `password_change`.
  - The value adds `signInNotice`, `retryAfterSeconds` (set when `error` came from a 429) and these methods:
    - `signIn(email, password, noticeDigest?)`
    - `lock()`: shows locked at once, then posts lock; a failure is ignored
    - `unlock(password)`
    - `changePassword(currentPassword, newPassword)`
  - `endSession` works from `signed_in`, `locked` and `password_change`.
- **`api/client.ts`:**
  - A 423 `session_locked` from any call runs the new `onLocked` hook.
  - A 401 runs `onUnauthenticated` unless the call is sign-in or setup, or the code is `invalid_credentials`.
- **`Gate`:**
  - `locked` after being signed in during this page load keeps the app mounted inside an element with `hidden` and `inert` (drafts survive, nothing is visible or focusable), next to `<LockScreen/>` in the auth frame. A page that loads into a locked session mounts only the lock screen.
  - `password_change` shows `<ChangePasswordPage forced/>` in the auth frame.
  - `signed_in` also mounts `<IdleLock/>`.
  - `/account/password` (a route inside Shell, not in the nav) shows `<ChangePasswordPage/>`.
- **`tooManyRequestsText(details)`** (`api/too-many.ts`):
  - seconds below 60 → "Too many requests. Try again in N seconds." (1 → "1 second")
  - 60 or more → "… in N minutes.", rounded up, "1 minute"
  - missing or invalid → "Too many requests. Try again later."
- **Idle lock (W2):**
  - Input is `keydown`, `pointerdown`, `pointermove`, `wheel` and `touchstart` on `window`. The last input time is shared across tabs through `localStorage['rampart.lastInputAt']` (ms), written at most once a second. If storage throws, each tab tracks itself.
  - Lock when `now − max(local, stored) ≥ SESSION_LOCK_AFTER_MS`.
  - **Keep-alive:** input arriving `SESSION_KEEPALIVE_MS` or more after the last keep-alive calls `refresh()`, so `last_seen_at` follows real input. There is no keep-alive without input, and none while locked.
  - Mounted only while `signed_in`.
- **Settings** sections: Assessment, Users (admin), Sign-in notice (admin), Audit log, numbered without gaps.
