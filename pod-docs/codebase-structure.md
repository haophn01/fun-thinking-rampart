# Codebase structure

_For agents: scout writes it and engineers read it before coding. You check it and fix what's wrong._

> High-level overview only — what the system is and how its parts fit. No file lists or deep directory trees: those change every sprint, and agents read the code for detail. Name a path only for a part's top-level folder.

The **`## Smoke recipe`** below tells each engineer how to bring the app up for browser verification (per `pod:engineer`'s instructions). Fill it in; engineers need it to verify their slices.

## What it is

Rampart (a placeholder name) is a self-hosted CMMC Level 2 readiness platform: one defense contractor runs it locally to assess the 320 NIST SP 800-171A Rev 2 objectives, see a live SPRS score and Conditional-status check, and keep a rules-checked POA&M. No CUI in V1.

## Parts

- `@rampart/catalog` (`packages/catalog`): the NIST SP 800-171 Rev 2 catalog as versioned data (families, requirements, objectives, SPRS points) with its types and loader.
- `@rampart/rules` (`packages/rules`): pure functions for requirement status, SPRS score, POA&M eligibility, the Conditional check and the 180-day clock; `@rampart/rules/poam` holds the cited regulation data. `ssp-lint` (`packages/rules/src/ssp-lint/`, re-exported from the package root) is the SSP pre-export check: `lintSspFrom(catalog, { view, assets, diagrams, review }, limits)` and its twelve rules in `SSP_LINT_RULES`, run by both the api and the web app; its zod mirror is `contract/ssp-lint.ts`.
- `@rampart/api` (`apps/api`): Fastify HTTP API under `/api`, the only writer of the SQLite database; `@rampart/api/contract` is the browser-safe contract (zod and constants such as `PRODUCT_NAME`).
- `apps/api/src/ssp-data` (part of the api): the SSP data api under `/api/ssp/*` (profile, roles, assets, diagram links, service providers, the responsibility matrix, document control), one folder per part with its own `routes.ts`, all registered by `registerSspDataRoutes` inside the guarded plugin. New code there imports `requireAssessmentId`, `utcDate`, `changedFields` and `newId` from `ssp-data/common.ts` instead of copying them. Its tables come from migration 0005; collection rows are removed softly (`removed_at`), never deleted.
- `apps/api/ssp` (part of the api, outside `src/`): the SSP export, v2. A pure outline (`model.ts` and `model/`, one file per group of sections) in the NIST SP 800-171 SSP order with the CMMC sections, approvals and two appendices, built from the catalog, both profiles, the SSP workspace data (roles, assets, providers, the matrix, diagram links, document control), the assessment view, the POA&M view, policies and evidence. `render.ts` turns it into a `.docx` with `docx`, deterministic apart from image media and relationship ids; `image-info.ts` reads PNG and JPEG sizes by hand; at most `SSP_MAX_EMBEDDED_IMAGES` diagrams are embedded and a CUI item never is. `ssp/testing/docx-text.ts` reads a `.docx` back as text for tests (the e2e specs reuse it).
- `@rampart/web` (`apps/web`): React 19 app built with Vite.
- `apps/web/src/pages/ssp` (part of the web app): the SSP workspace. `/ssp` is one page with six tabs in `?tab=` (`SSP_TABS` in `tabs.ts`), one prop-less module per tab in `tabs/` that fetches its own data, and a shared kit in `kit/` (`useLoad`, `Section`, `LoadError`, `SspProfileForm`, `SspTable` that stacks into cards under 768 px, `RemoveButton`, `errorText`/`fieldErrors`, and the `kit/testing.tsx` fetch stub for tab tests). New tab code uses the kit instead of copying it.
- `templates/` (repo root, not a package): reference copies of the official NIST and DoD SSP, POA&M and assessment files, with each source`s URL, date checked, terms and SHA-256 in `templates/SOURCES.md`; vendor templates are links only. Nothing imports it.

## How they connect

- **Production path** (`pnpm start`, and `pnpm e2e`): one process, the built api with `SERVE_WEB=true`, serves the built web app (`apps/web/dist`, read once into a manifest by `security/web-app.ts`) and `/api` on `WEB_PORT` (default 3000). Page paths fall back to `index.html`; a missing asset or api path is the JSON 404.
- **Dev path** (`pnpm dev`, unchanged): browser → web (Vite) on `WEB_PORT`, and Vite proxies `/api` to the api on `127.0.0.1:${API_PORT}`. Vite sends no CSP, so CSP behaviour is checked only on the production path.
- web imports `@rampart/api/contract` (contract only, never server code), `@rampart/catalog` and `@rampart/rules` (for the live what-if score).
- api imports `@rampart/rules` and `@rampart/catalog`; rules imports catalog. Nothing imports web or api internals.
- Internal packages export TypeScript source (`exports` → `./src/*.ts`); only the apps build. tsup bundles the workspace packages into `apps/api/dist`, and Vite bundles the web app.
- State lives only in one SQLite file written by the api (from the API and DB skeleton slice on).

## Stack & conventions

- **Runtime and packages:** Node `>=24`; pnpm (pinned in the root `packageManager`, enabled with corepack); pnpm workspace `packages/*` and `apps/*`; every package is `"type": "module"`. `pnpm-workspace.yaml` allows only the `better-sqlite3`, `@node-rs/argon2` and `esbuild` build scripts (`strictDepBuilds`) and refuses versions published less than a day ago (`minimumReleaseAge: 1440`), trust downgrades and exotic subdependencies.
- **Lockfile frozen after bootstrap:** later slices may edit `scripts` in a package.json they own, never dependencies.
- **TypeScript 6** with `moduleResolution: "Bundler"` and strict flags in `tsconfig.base.json` (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `verbatimModuleSyntax`, `isolatedModules`). Each package has a `tsconfig.json` extending it and a `typecheck` script (`tsc --noEmit`); the root `tsconfig.json` covers `tests/`, `e2e/`, `scripts/` and root config files for the linter. Source imports are extensionless; config files that Vite or Node load directly (`vite.config.ts`) import with a `.ts` extension.
- **Lint and format:** ESLint flat config (`eslint.config.js`) with typescript-eslint `strictTypeChecked` (type-aware through the project service), react-hooks and eslint-config-prettier. Prettier: single quotes, width 100, `endOfLine: "lf"`; `.gitattributes` forces LF so Windows checkouts pass `prettier --check`. The frozen contract files `packages/catalog/src/types.ts`, `packages/rules/src/types.ts` and `packages/rules/src/errors.ts` are in `.prettierignore` so they stay word for word as the sprint doc writes them.
- **Tests:** Vitest at the root (`vitest.config.ts`) with projects `packages/*`, `apps/*` and `repo` (`tests/**/*.test.ts`). Globals are off: import `describe`/`it`/`expect` from `vitest`. The web project uses jsdom, Testing Library and jest-dom matchers (`apps/web/src/test-setup.ts`); the api is tested through `buildApp()` and `app.inject`.
- **Servers:** everything binds `127.0.0.1`. `pnpm start` serves everything on `WEB_PORT` (default 3000; it sets the api's `API_PORT` to it, so 3001 isn't used). In `pnpm dev`, `WEB_PORT` defaults to 3000 and `API_PORT` to 3001; Vite uses `strictPort`, and `apps/web/dev-ports.ts` validates both (integers 1–65535, different from each other).
- **Security baseline** (`apps/api/src/security/`): `HOSTED`, `SERVE_WEB`, `WEB_DIST_PATH` and `RATE_LIMIT_MULTIPLIER` in config; `assertSafeStartup` refuses hosted mode without `SERVE_WEB`, with a multiplier other than 1, or at `debug`/`trace`. Pages get the web CSP (`default-src 'self'; …`, no inline, no eval; hosted adds `upgrade-insecure-requests`), `/api` keeps its own CSP; HSTS only when hosted. Rate limits: 600/min per IP, 10/min per IP each for setup, sign-in, change password and unlock (`AUTH_LIMITED_ROUTES`), 429 `too_many_attempts` with `Retry-After`. `ROUTE_MATRIX` pins every api route's access. zod under the CSP: zod probes `Function('')` when each object schema is built, which the CSP blocks and reports, so the contract's first module (`contract/browser.ts`) sets `z.config({ jitless: true })` when it loads where a DOM exists, and `apps/web/src/main.tsx` imports `@rampart/api/contract` first. A call in app code would run too late (imports build the schemas first). The api, in Node, keeps JIT.
- **API:** `buildApp({ config, db, now? })` in `apps/api` builds the Fastify app (`now` is the app clock; every expiry, lockout and audit `at` comes from it); `server.ts` only wires config → open DB → migrate → listen. Config is zod-validated env (`ConfigError` names every bad key). Errors always leave as the contract's envelope (`{ error: { code, message, requestId, details? } }`): throw `AppError(code, …)` for an expected failure, let zod input errors become `validation_failed`, and anything else becomes a generic 500. Handlers return `respond(schema, payload)` so responses are checked against the contract. Logs are pino JSON with a `requestId` on each line and secrets redacted.
- **Auth guard:** `registerApiRoutes(app, deps)` (`apps/api/src/routes/index.ts`) registers every session route in one encapsulated plugin whose `onRequest` guard is deny-by-default: a route needs a session unless it sets `config: { public: true }`; writes on a session need `x-csrf-token` (`skipCsrf: true` only for setup and sign-in); `config: { role: 'admin' }` limits a route to admins. Order: 401 → 403 `csrf_failed` → 423 `session_locked` → 403 `password_change_required` → 403 `forbidden` → 400 → 404; a locked session may reach only `LOCKED_SESSION_ROUTES` (lock, unlock) and a session with a temporary password only `PASSWORD_CHANGE_ROUTES` (those plus change password), both pinned in `auth/guard.ts`; public routes are never gated by either. The handler reads the session from `request.auth` (with `locked` and `mustChangePassword`). Add new api routes inside that plugin; health and test-only routes stay on the root. Sessions, passwords and lockout live in `apps/api/src/auth/`; every change writes `recordAudit(tx, …)` inside its transaction.
- **Sessions and passwords (sec-auth):** a session ends 30 min after `last_seen_at` or 8 h after `created_at` (`SESSION_IDLE_LIMIT_MS`, `SESSION_ABSOLUTE_LIMIT_MS` in `contract/auth.ts`; cookie `Max-Age=28800`); `rotateSession` keeps `created_at`. A locked session (`session.locked_at`) never moves `last_seen_at` until it unlocks. `auth/lockout.ts` counts sign-in, unlock and change failures in one run of 5. `auth/password-policy.ts` checks the bundled blocklist (`auth/blocklist/`, offline, applied only when a password is set) and reuse against the current hash and the newest 4 `password_history` rows. An admin-set password (create or reset) sets `user.must_change_password`. The sign-in notice is the one `settings` row (`apps/api/src/settings/`); sign-in needs its `noticeDigest` while it is set. The web side: `useSession()` adds `locked` and `password_change` statuses; `auth/Gate.tsx` shows `LockScreen` (the app kept mounted, `hidden` and `inert`) or the forced `ChangePasswordPage`, and mounts `IdleLock` while signed in (15 min, `localStorage['rampart.lastInputAt']` shared across tabs).
- **Assessment api:** `apps/api/src/assessment/` keeps the routes as glue (parse, call, `respond`) and the logic in its repository: the active assessment is the earliest-created row, every response's `evaluation` is `evaluateAssessment(loadCatalog(), <stored rows>, REGULATION)`, and each write runs with its audit event in one transaction.
- **API tests:** `createHarness()` (`apps/api/src/testing/harness.ts`) gives an app on a migrated in-memory DB with a settable `clock`, `setupAdmin()`, `signIn()` and a `client()` that keeps the cookie and sends the CSRF header; it captures log lines in `logs`. `signIn(email, password)` clears `must_change_password` first, so a user an admin created can sign straight in; pass `{ temporary: true }` to keep the flag and test the forced change.
- **DB:** better-sqlite3 with Drizzle; schema in `apps/api/db/schema.ts`, SQL migrations generated by drizzle-kit into `apps/api/db/migrations` (never hand-edited after commit).
- **Product name:** only `PRODUCT_NAME` in `@rampart/api/contract` spells it.

## CI

`.github/workflows/pod-ci.yml`, on `pull_request` and on `push` to `main`, with `permissions: contents: read, pull-requests: read`:

- **verify** (matrix `ubuntu-latest`, `windows-latest`): checkout, setup-node 24 (`package-manager-cache: false`, since its default cache calls pnpm before `corepack enable`), `corepack enable`, `pnpm install --frozen-lockfile`, `pnpm verify`.
- **secrets** (ubuntu): checkout with `fetch-depth: 0`, then `gitleaks/gitleaks-action@v2` with `GITHUB_TOKEN`.
- **e2e** (matrix `ubuntu-latest`, `windows-latest`, `fail-fast: false`, 20-minute timeout): the same setup as verify, then `pnpm exec playwright install --with-deps chromium`, `pnpm e2e`, and on failure uploads `playwright-report/` and `test-results/` as an artifact. A job of its own, so the browser download never slows verify.
- **audit** (ubuntu): `node scripts/audit-gate.ts` on the repo (fails on a high or critical advisory not in `audit-allowlist.json`), then the same gate with `--expect-findings` on `tests/fixtures/supply-chain/vulnerable`, proving it fails on a known advisory.
- **semgrep** (ubuntu, the `semgrep/semgrep` image pinned by digest): `semgrep scan` with `p/default`, `p/typescript` and `p/react` at ERROR severity.
- Every `uses:` is pinned to a commit SHA with a `# v<version>` comment. `tests/repo/ci-workflow.test.ts` pins all five jobs; change the test with the workflow.

## Smoke recipe

- **Install:** `corepack pnpm start` from a clean clone installs (frozen lockfile), builds, migrates and serves everything (the built pages and `/api`) from one server on `WEB_PORT`, default 3000 (`scripts/start.ts`; it sets `SERVE_WEB=true` and `API_PORT` to `WEB_PORT`; 3001 is gone from this path). It needs a pnpm on PATH for its steps: with only corepack, put a `pnpm.cmd` and an sh `pnpm` shim (`exec corepack pnpm "$@"`) first on PATH. To install only: `corepack pnpm install --frozen-lockfile`. For plain `pnpm`, run `corepack enable`; if that fails with `EPERM` (Node's folder isn't writable, as with nvm4w on the dev machine), use `corepack enable --install-directory <a folder on your PATH> pnpm`, or keep calling `corepack pnpm …`. End-to-end: `pnpm exec playwright install chromium` once, then `pnpm e2e` (it builds, then one production-path server on 3290 with a fresh temp DB; `auth.spec.ts` adds a production-path server on 3295, `look.spec.ts` an api on 3293 and `security.spec.ts` a hosted server on 3294).
- **Start commands:** production path (what users run, and the one with the CSP): `WEB_PORT=<web> corepack pnpm start` (bash) or `$env:WEB_PORT=<web>; corepack pnpm start` (PowerShell); or, already built, `SERVE_WEB=true API_PORT=<web> pnpm --filter @rampart/api start`. Everything is on `http://127.0.0.1:<web>/`. Development (unchanged): `API_PORT=<api> WEB_PORT=<web> pnpm dev` (bash), or `$env:API_PORT=<api>; $env:WEB_PORT=<web>; pnpm dev` (PowerShell), Vite with hot reload on `<web>` and the api on `<api>`. Either way one command; stop it with Ctrl+C. For many sign-ins in a row, add `RATE_LIMIT_MULTIPLIER=100` (local mode only).
- **DB setup:** migrations run when the api starts, or run `pnpm db:migrate`. The database is `apps/api/data/rampart.sqlite` unless `DATABASE_PATH` says otherwise (use a scratch path to keep runs apart). No seed yet.
- **Login credentials:** none are seeded. On a fresh database the first run shows Setup, where you create the admin (any email, a password of 12 or more characters that isn't on the common-password list: avoid things like `PassWord1234` or one character 12 times); then sign in with it. Without the web UI: `POST /api/setup` with `{ email, displayName, password }`, keep the `rampart_session` cookie and send `csrfToken` as `x-csrf-token` on writes. If a sign-in notice is set, `POST /api/session` also needs `noticeDigest`, the `signInNotice.digest` from `GET /api/session` (400 `notice_not_acknowledged` without it).
- **Temporary passwords:** a user you add under Settings › Users (or whose password you reset) gets a temporary password: their first sign-in shows only "Change password" (`data-testid="change-password-forced"`), and every other api route answers 403 `password_change_required` until `POST /api/session/password` `{ currentPassword, newPassword }` succeeds. A role change or reset signs that user out everywhere. To check a contributor's view quickly, add them, sign in as them and pick a new password, or change it through the api.
- **Session lock:** the web app locks after 15 minutes without input. Don't wait for it: `POST /api/session/lock` (with the CSRF header and no body) locks the session at once (204) and a reload shows the lock screen ("Session locked", "Password", Unlock / Sign out); in Playwright, `page.clock.install()` before the page loads, then `page.clock.fastForward('15:00')`. While locked every route but lock, unlock and the public ones answers 423 `session_locked`; `POST /api/session/unlock` `{ password }` unlocks.
- **Sign-in notice:** Settings › Sign-in notice (admin), "Save notice" or "Clear"; `PUT /api/settings/sign-in-notice` `{ text }` (`null` clears). While it is set, the Sign in page shows it first and the form only after "Acknowledge and continue".
- **Key URLs:** web routes `http://127.0.0.1:<web>/` (Dashboard: SPRS ruler, feature control frame, HOLD/ACCEPT stamp, Conditional check, objectives, families, needs attention), `/assessment` (families, requirements, objective status, live and what-if score; `?family=AC&req=AC.L2-3.1.20` opens a requirement), `/poam` (closeout clock, candidates, items), `/evidence` (items, file uploads with SHA-256, CUI references), `/policies` (files and requirement links), `/ssp` (the SSP workspace; `/ssp?tab=<id>` opens a tab, and no tab or an unknown one opens Identification: `identification` (Identification & roles: the system profile form, identification fields, roles), `environment` (CUI description, system environment, diagrams), `assets` (inventory by asset category), `providers` (service providers and the responsibility matrix), `document-control` (review status and schedule, record of changes, approvals) and `export` (Lint & export: 1 readiness, 2 the pre-export check, 3 "Export SSP (.docx)")) `/settings` (assessment type and Conditional Status Date, users, the sign-in notice for admins, audit log) and `/account/password` (Change password, linked from the masthead, not in the nav); any other path shows "Page not found". The shell calls health on load and shows a "Can't reach the API" alert with Retry when the api is down, or "Too many requests. Try again in N seconds." with Retry on a 429. Api: `http://127.0.0.1:<api>/api/health` (public) and `/api/session` (public; reports `setupRequired`, `locked`, `mustChangePassword`, `signInNotice`, and the `csrfToken` writes need; `POST /api/session/lock`, `/unlock` and `/password` need a session); every other route needs a session: `/api/assessment` (writes: `PUT /api/assessment/objectives/<URL-encoded objective ID>`, `PATCH /api/assessment/requirements/<requirement ID>`, admin-only `PATCH /api/assessment`), `/api/poam`, `/api/evidence`, `/api/policies` (uploads are raw `application/octet-stream` bodies with the name in `x-file-name`), `GET`/`PATCH /api/system-profile`, `GET /api/ssp/export` (the v2 `.docx`; each export appends an `export` revision, "Exported as <file name>", to the record of changes after the render succeeds), `GET /api/ssp/lint` (the pre-export check: `{ version, findings, counts }`, writes nothing), the SSP data routes (`GET`/`PATCH /api/ssp/profile`; list, `POST`, `PATCH /:id` and soft `DELETE /:id` on `/api/ssp/roles`, `/api/ssp/assets`, `/api/ssp/diagrams` and `/api/ssp/providers`; `GET /api/ssp/responsibilities` and `PUT /api/ssp/responsibilities/<requirement ID>`; `GET /api/ssp/document-control`, `POST /api/ssp/revisions`, and admin-only `POST`, `PATCH /:id`, `DELETE /:id` on `/api/ssp/approvals`) and `/api/audit`. The api is also reachable through the web origin at `http://127.0.0.1:<web>/api/health` (same server on the production path; Vite's proxy in dev).
- **End-to-end:** `pnpm e2e` runs `auth.spec.ts` first (its own production-path server on 3295 with its own fresh database: the sign-in notice set in Settings and acknowledged at sign-in, then in the audit log; an admin-created user's forced change refusing a too-common and a reused password; and the idle lock driven by `page.clock`, a wrong password refused and the right one unlocking), then `look.spec.ts` (its own api on 3293 with its own database, seeded through that api once, with data on every page and every SSP tab; it checks the Look on each nav route, the assessment detail and all six `/ssp?tab=<id>` views, and that the seeded workspace shows its data, a future-tense finding on Lint & export included, plus the auth screens (sign-in notice, forced change, lock screen, Change password, Settings with a notice, the shell's 429); the browser's `/api` calls are routed to it, the pages come from the config's server under its CSP, and every page records zero `securitypolicyviolation` events), then `security.spec.ts` (signed-out reads only on 3290: the exact web CSP and headers on `/` and `/assessment`, the api CSP on `/api/health`, hashed immutable `/assets/` only, the app loading with no CSP violation; plus its own `HOSTED=true` server on 3294 for HSTS and the `__Host-rampart_session` Set-Cookie, kept to a few requests since hosted limits are real), then `shell.spec.ts` and `smoke.spec.ts` (the plan's Verification path, then the SSP workspace filled, the pre-export check compared with `GET /api/ssp/lint`, and the v2 export read back; its upload and diagram helpers are in `e2e/helpers/api.ts`) on the config's server (3290, fresh temp DB). The config's server keeps one database for the whole run and specs run in file-name order; `shell` and `smoke` need a fresh install, so a spec that signs in or writes on that server must sort after `smoke.spec.ts`, or only read signed out (as `security.spec.ts` does), or start its own server (as `auth.spec.ts`, `look.spec.ts` and `security.spec.ts`'s hosted check do). Fixed e2e ports: 3290, 3293, 3294, 3295; every non-hosted server sets `RATE_LIMIT_MULTIPLIER=100`.
- **Verification:** `pnpm verify`
