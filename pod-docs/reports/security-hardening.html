At a glance

Goal: make Rampart meet, itself, the NIST SP 800-171 requirements it touches (the human chose "Security Protection Asset"), and close the web-app gaps from the research. No screenshots: this report has none, by the human's preference.

Shipped:

  • Baseline: an access-control test over every api route (401, 403, CSRF, IDOR); SHA-pinned actions, an audit gate and Semgrep in CI; the production web build served by the api with a strict CSP; HOSTED=true mode; rate limits; log-redaction tests.
  • Auth: 30 min idle and 8 h sessions, a 15 min lock screen, an offline password blocklist, no reuse of the last 5, a change-password page, temporary passwords, an admin-set sign-in notice.
  • MFA: TOTP required for every account, with 10 single-use recovery codes, a replay guard, encrypted secrets, an admin reset and a pnpm admin:reset-mfa CLI.
  • Integrity: uploads checked by their real bytes with a zip-bomb guard, a hash-chained audit log with a Verify audit log button, a FIPS_MODE check with a PBKDF2 option, and SECURITY.md (disclosure, STRIDE, 15 requirements mapped to code and tests).

Key features

No UI shots here. Each is something a user can do now.

  • Sign in with a second step. Password, then a 6-digit authenticator code or a recovery code. An account with no app sees a QR code and key, confirms once, and is shown 10 recovery codes once. Admins reset a user's MFA under Settings › Users. Details: mfa.
  • Safer sessions and passwords. A session ends after 30 min idle or 8 h; the page locks after 15 min without input and only the password unlocks it; common passwords and the last 5 are refused; a temporary password must be changed first; an admin can set a sign-in notice that must be acknowledged. Details: setup and sign-in.
  • Verify the audit log. Settings › Audit log › Verify audit log says "Audit log intact" with the event count and newest hash, or names the first broken event. Details: audit log.
  • Uploads are judged by their bytes. A program renamed .pdf, an SVG, an HTML file and a zip-bomb .docx are refused with a clear message; real PDF, PNG, JPEG, DOCX, XLSX and text are accepted. Details: evidence, policies.
  • Run it hosted-ready. pnpm build then pnpm start serves one origin with the strict CSP; HOSTED=true adds HSTS, a __Host- Secure cookie and a proxy setting; FIPS_MODE=required refuses to start without FIPS crypto.

How it fits together, as built

The built shape matches the plan's: the api serves the web build, and requests pass headers, rate limit, then the guard, which sends them to auth, MFA, uploads or the audit chain, all on one SQLite file.

  • http hardening: apps/api/src/app.ts uses security/headers.ts, rate-limit.ts and web-app.ts (production static serving).
  • security config: apps/api/src/config.ts and security/startup.ts, secret-key.ts, secrets.ts.
  • auth: auth/guard.ts (gate order CSRF → lock → MFA → must-change → role), sessions.ts, routes.ts, session-routes.ts, password.ts, password-policy.ts, lockout.ts. Routes join the guard in routes/index.ts.
  • mfa: auth/mfa/ (totp.ts, recovery-codes.ts, qr.ts, reset.ts, cli.ts, routes.ts).
  • uploads: uploads/upload.ts calls file-check.ts, zip.ts and file-name.ts; evidence and policies routes use it.
  • audit chain: audit/record.ts hashes on write; chain.ts verifies and backfills; prepare.ts runs the backfill at start.
  • web: apps/web/src/auth/ (session.tsx, Gate.tsx, useIdleLock.ts, MFA pages, ChangePasswordPage.tsx); the verify button is in pages/settings.
  • CI and tests: .github/workflows/pod-ci.yml, scripts/audit-gate.ts, security/route-matrix.test.ts, e2e/security.spec.ts, e2e/auth.spec.ts.
